# History — August 2026

Narrative log of decisions made across Claude Code sessions on this project.
`CLAUDE.md` is the current-state handoff (what exists now, what's
unverified); this file is the **why**, in order, so you don't have to
reconstruct it from `git log` or re-explain context to a fresh session.

## 2026-08-03 — Windows port (earlier session)

`SendInput`-based keystrokes, loopback MIDI attach instead of virtual-port

## 2026-08-07 — Long session: SDK 2.0, Ctrl+K dispatch, rebrand

### 1. Per-user command catalog

**Problem:** every user has different installed macros, so a command list
can't ship as a static file. **Decision:** `keyscheme.py`'s `parse_keyscheme()`
now emits a `catalog` — every command in the `.keyscheme`, not just ones with
a shortcut, with macro names decoded from Base64. New MCP tool
`studio_one_generate_command_catalog` lets the user regenerate it themselves,
from either the DAW's own folders or an arbitrary file. Verified against the
real export: 1751 commands, 471/471 macros decoded correctly.

**Side finding, confirmed on this machine:** the vendor folder is `Fender`,
not `PreSonus` (`%APPDATA%\Fender\Studio Pro 8\`), and macro exports go to
`Documents\Studio Pro\Macros`, not `Documents\Studio One\Macros`. Both were
previously guessed. Fixed in `plugin_db.py`/`macro_writer.py`.

### 2. MCP SDK 2.0 upgrade + dual transport

**Problem:** pinned to `mcp<2` because 2.0 removed the
`@server.list_tools()`/`@server.call_tool()` decorator API `server.py` relied
on. **Decision:** rather than rewrite onto the new high-level
`MCPServer`/FastMCP decorator style, adapted to the lowlevel `Server`'s new
constructor callbacks (`on_list_tools`, `on_call_tool`) — zero changes to any
of the six `tools/*.py` dispatch modules. This also unlocked
`Server.streamable_http_app()`, so `--transport {stdio,http}` now serves the
same tools over stdio (Claude Desktop, unchanged default) or local HTTP.
Verified with real `mcp.client` sessions over both transports.

### 3. LICENSE, credits, and the move to its own repo

Neither this fork nor upstream ever shipped a real `LICENSE` file — "MIT" was
only ever a README claim. Added one crediting both `tiwadara` (original) and
this fork. The user then split this project off `pajdarova/StudioOneMcp` into
its own repo, `pajdarova/FenderStudioProMCP` (already MIT-licensed on
GitHub) — merged with `--allow-unrelated-histories -X ours` so the new repo's
initial commit stays in the history and this project's LICENSE (with
attribution) wins the merge. Local `main` now tracks `fender/main`. The old
`pajdarova/StudioOneMcp` fork was later deleted by the user once full history
preservation was verified (`git log fender/main..origin/*` empty on both
`main` and `windows-support`).

### 4. Ctrl+K command-palette dispatch replaces MIDI-CC — confirmed live

**Problem:** `studio_one_run_command` dispatched through
`docs/midi-map.json` over MIDI CC — 224 built-ins, zero macros, and
documented as unreliable (channel collision with Mackie Control's V-Pots,
never confirmed firing upstream). **Decision:** resolve against the
per-user catalog (§1) instead, and dispatch by typing the command's readable
name into the DAW's `Ctrl+K` palette (`KEYEVENTF_UNICODE`, layout-independent).
Added `studio_one_save_new_version` for the LLM to call before risky
multi-step work — an explicit tool, not automatic on every command, so it
doesn't fire on trivial single actions.

**This is the first command-dispatch path in the project's history confirmed
to work.** Live-tested against the running DAW with the user watching:
`studio_one_run_command("Undo")` actually undid the last action. Along the
way, discovered that panel toggles like "Toggle Mixer" aren't in the
`.keyscheme` catalog at all (they resolve under a different internal label —
`View|Console`, displayed as `"Console"`) — not a bug, just a naming trap;
logged as an open item.

### 6. CI was never actually green — fixed the real reasons

Pushing to the new repo surfaced that `mypy --strict` had been failing on CI
(`ubuntu-latest`) since Windows support landed, unnoticed because local
sessions only compared "error count vs. before my change," not exit code.
Two distinct causes, both platform-divergence traps:

- **mypy:** `ctypes.WinDLL` only exists in typeshed's win32-conditional
  stubs. Reproduced locally with `mypy src --platform linux`; fixed by
  pinning `platform = "win32"` in `[tool.mypy]` so CI and a Windows dev
  machine see the same stubs regardless of which OS actually runs mypy.
  Also deleted `src/studio_pro_mcp/commands.py` — the old MIDI-CC
  dispatcher, unreferenced since §4, whose `Any`-leaking `load_map()` was
  one of the mypy failures.
- **pytest:** the inverse trap. `test_tools_transport.py`/`test_tools_mixer.py`
  fail locally on this Windows machine (`MidiBridge._open_existing_port()`,
  the Windows-only loopback-attach path, doesn't match how the `bridge`
  fixture mocks `rtmidi.MidiOut`) but **pass cleanly on Linux CI**, because
  `MidiBridge.open()` takes the `open_virtual_port()` branch there instead.
  So: green CI is not proof these MIDI paths work on Windows — they test a
  code path Windows never executes. Fixture still needs fixing — now tracked
  in `TASKS.md`.

## 2026-08-08 — Bridge fixture fix; Ctrl+K reliability finding

### 10. `bridge` test fixture fixed — 181/181 tests green on Windows

Root cause: a bare `MagicMock()` defaults `__iter__` to an empty iterator, so
`enumerate(available)` in `MidiBridge._open_existing_port()` (the Windows
loopback-attach path) never found a match against the fixture's mocked
`rtmidi.MidiOut`, regardless of what `port_name` the test used. Fix:
`mock_out.get_ports.return_value = [port_name]` in the three affected test
files. Works on both branches since `open_virtual_port()` (non-Windows)
ignores `get_ports()` entirely. First time this session Windows and Linux CI
fully agree: 181/181 local, all three CI jobs green.

### 11. Ctrl+K dispatch is unreliable for short/ambiguous queries — fixed by preferring the catalog shortcut

Live-testing task item 1 (the 8 commands with an "untranslatable" `.keyscheme`
shortcut) found two things:

- **7 of 8 actually have a working alternate shortcut already** (`Stop` →
  `num0`, `Record` → `nummultiply`, `Rewind`/`Forward` → `numminus`/`numplus`,
  `Toggle Start` → `space`, etc.) — the "unsupported key" entries in
  `.keyscheme` were a *second*, redundant multimedia-key binding for the same
  command; `keyscheme.py` already picks the translatable one. Only
  `Devices|All Notes Off` has no usable shortcut at all.
- **Ctrl+K's result list doesn't reliably highlight the exact match for short
  queries.** Confirmed live: typing "Stop" (12 substring matches in the
  catalog, e.g. "Stop Cell", "Stop at End of Bar") landed on an unrelated
  result, not `Transport|Stop`, and pressing Down didn't fix it either — a
  multi-round live debugging session with screen-sharing narration confirmed
  the search field had the right text but the palette's selection logic
  isn't exact-match-first. `Undo` had worked earlier by what looks like
  coincidence, not because the palette behaves reliably in general.

**Fix:** `tools/commands.py` now checks the catalog's `shortcut` field first
and dispatches via `keystrokes.send_command()` (a single deterministic
keypress, still per-user since it reads the live-generated shortcuts config)
when one exists; Ctrl+K (`run_via_command_palette`) is now a fallback only
for commands/macros with no assigned shortcut. `send_command()` gained a
`confirm_dialog` parameter (reuses the existing `dialog.confirm` mechanism
already used elsewhere in `keystrokes.py`) so `studio_one_save_new_version`
works the same way regardless of dispatch path. Also fixed a latent bug this
uncovered: the hardcoded query was `"Save New Version..."` (with ellipsis)
but the real catalog label has no ellipsis — would never have matched.

**Also fixed in passing:** the per-user catalog config path moved from
`~/.studio_one_mcp/` to `~/.studio_pro_mcp/` during the rename (§5,
2026-08-07) but nobody regenerated the file at the new path — the first live
test today failed with "no command catalog found" until
`studio_one_generate_command_catalog` was re-run.

Live-verified end to end: `studio_one_run_command("Stop")` now reliably
stops playback via the direct `NumPad0` shortcut, no Ctrl+K involved.

An unrelated but useful side question came up during this debugging: can
keyboard *shortcuts* (modifier combos like Ctrl+Z) be sent the same
layout-independent way as the Ctrl+K search text (`KEYEVENTF_UNICODE`)? No —
`KEYEVENTF_UNICODE` is a text-input path (`WM_CHAR`-equivalent); modifier
accelerators are consumed via `WM_KEYDOWN` + virtual-key codes, a different
OS mechanism entirely, so they can't be unified. Letters/digits/function
keys/numpad are already layout-independent via VK codes for this purpose;
only OEM punctuation keys have the layout-dependency problem `keyscheme.py`
already works around by ranking alternatives.

### 12. MCU port renamed to `StudioPro-MCU`; 3-port split simplified

`TASKS.md`'s "split into three ports" was motivated by a real collision:
`MCPPads.surface.xml` (SURF) uses CC 0–127/0–95 on channel 0/1, overlapping
MCU's V-Pot range (CC 16–23) — a genuine problem *if both devices actually
receive on the same port*. Investigating it found that premise no longer
holds: SURF CC dispatch is dead code (§4/§11 — Ctrl+K/direct shortcuts
replaced it), and `MidiBridge.press_cc()` — the only method that could fire
a SURF CC — had zero callers. Only MCU uses the shared port today, and MCU
doesn't collide with itself.

Before deciding, asked which protocol has more headroom: **MCU over HUI** —
14-bit fader resolution, richer LCD/metering, wider DAW support, extendable;
HUI is older, coarser, mainly a Pro Tools-compatibility fallback. This
codebase already implements MCU, confirmed the right choice.

**Decision:** rename the port (`StudioOneMCP` → `StudioPro-MCU`) so its name
reflects what it actually carries, delete `press_cc()` as confirmed-dead
code (same rationale as deleting `src/studio_pro_mcp/commands.py` in §11),
and leave `StudioPro-SURF`/`StudioPro-MIDI` as unbuilt ideas — no code
exists for either, so giving them ports now would be speculative. If SURF
CC dispatch is ever revived, or note-level MIDI I/O (roadmap #5) gets built,
*then* they get real ports.

**Done same day:** user recreated the loopMIDI port and rebound the DAW's
Mackie Control External Device to `StudioPro-MCU`. Live-verified:
`--list-ports` shows it, `MidiBridge.open()` attaches, `mixer_get_state`
responds over a real MCP client session.

### 13. Future idea: read real transport state via MIDI Clock/MTC

While reconnecting the External Device, the user noticed Fender Studio Pro
also offers `MIDI Clock`, `MIDI Clock Start`, and `MIDI Timecode` as
separate External Device sync outputs. Motivation for eventually reading
these: `mixer_get_state` today only returns an *optimistic* cache — what
`MidiBridge` last sent, not confirmed DAW state, because MCU as implemented
here is write-only. MIDI Clock Start/Stop would give real play/stop state;
MTC would give real playhead position — both useful context for an LLM
deciding whether/how to act (e.g. don't dispatch commands while genuinely
recording). Not scoped or built — recorded as motivation, not a task ready
to implement.

**Correction (same day):** first pass here claimed this needs a separate
port from `StudioPro-MCU` "because it's a continuous realtime stream" — that
reasoning was a loose analogy to the real SURF/MCU CC collision (§12), not
an actual protocol check. Checked: MIDI Clock/Start/Stop/Continue (System
Real-Time, status `0xF8`/`0xFA`–`0xFC`) and MTC quarter-frame (System Common,
`0xF1`) use status bytes that don't overlap MCU's channel-voice messages
(`0x8n`–`0xEn`) at all — unlike SURF, which genuinely shared CC numbers with
MCU's V-Pots on the same channel. Real hardware routinely runs MCU + Clock +
MTC over one physical MIDI cable with no conflict. The actual blocker is
different: `MidiBridge` only opens a `MidiOut` (send-only) today; reading
Clock/MTC means Studio One sending data *back*, which needs a `MidiIn` this
code doesn't have yet. Whether that read path ends up on the same port
(bidirectional) or a dedicated one is an open question for whenever this
gets built, not a settled requirement.

### 14. MCU play/stop live-verified; anti-clipping metering idea

Live-tested `transport_play`/`transport_stop` over the renamed
`StudioPro-MCU` port through a real MCP client session — user confirmed
playback started and stopped as expected. First real MCU confirmation since
the rename.

User then raised a concrete use case for the `MidiIn`/read-back idea in §13:
an LLM watching mixer levels to catch clipping. Discussed whether to depend
on a third-party MCU library — searched and found
[EMATech/PythonMcu](https://github.com/EMATech/PythonMcu) as the closest
candidate ("Mackie Host Controller written in Python"), but couldn't verify
its role fits ours (we emulate the *surface* sending to Studio One, not a
*host* receiving from a surface — the naming suggests the opposite role) or
its maintenance quality without reading the source. Decided: implement MCU
input parsing independently, same as everything else in this project — the
input/feedback side of MCU is a well-documented, stable, reverse-engineered
spec used by lots of third-party hardware, so this isn't guesswork the way
depending on an unverified library's fit would be.

**Scoped workflow, user-specified:** LLM reads meter levels, detects
clipping, *warns* the user — does not auto-adjust anything. User then gives
an explicit instruction (e.g. "pull all groups down by 3dB") and the LLM
executes that as a confirmed action. Matches the reversible/irreversible
split already established for voice input (`memory/brainstorm_panel.md`) —
reading state is passive/safe, adjusting the mix is a real action and needs
the user's word first.

**Not yet done:** verifying what meter messages Studio Pro's MCU
implementation actually sends (DAW implementations vary here) — needs a
`MidiIn` probe against the real installation before any parsing code gets
written, same "verify against the real thing" principle as everything else
this project has built. No code started; recorded in `TASKS.md`.

### 15. `MidiBridge` gains real MIDI input — confirmed live, fader feedback works

Built to unblock a concrete test: lower the HELPERS channel to -12dB, then
restore it to its current value — impossible without first knowing the
current value, which the write-only `MidiBridge` couldn't provide.

`MidiBridge.open()` now opens a paired `MidiIn` alongside the existing
`MidiOut` (same Windows-loopback-attach-by-substring vs.
`open_virtual_port()` branching, generalized `_open_existing_port()` to
take either port type). `_on_midi_in()` parses incoming pitch-bend messages
and writes into the *existing* `_fader_levels` cache — `mixer_get_state`
now reflects confirmed values with zero changes needed in `tools/mixer.py`.

**Live-verified the plan's open question, with a real answer:** ran a
diagnostic listener for 20s while the user moved faders by hand. Studio Pro
*does* echo fader position back over MCU on manual touch/move — captured 98
pitch-bend messages across three channels (`0xE1`, `0xE3`, `0xE8`=master),
correctly parsed into `{1: 37.3%, 3: 68.7%, 'master': 4.25%}`. This confirms
the HELPERS restore-to-current-value workflow is viable, with one caveat:
feedback only arrives when the fader is actually touched/moved (by a human
or, presumably, by us sending `set_fader`) — there's no evidence yet that
Studio Pro pushes current state for an *untouched* channel on demand, so
reading "current value" for a channel nobody has touched this session may
need a small manual nudge first.

187/187 tests (6 new: pitch-bend parsing for a regular channel, zero value,
master-channel key mapping, confirmed feedback overriding an optimistic
send, non-pitch-bend messages ignored, short/malformed messages ignored),
ruff and mypy clean.

### 16. HELPERS fader round-trip — full read→write→restore, live, works end to end

The actual test this was all built for. Channel 0, bank 0.

1. **Read current value:** a plain click didn't produce feedback (position
   didn't change, so no pitch-bend message — consistent with §15's finding
   that feedback only fires on an actual value change). Asked the user to
   nudge/drag instead — captured `84.33` (0–100 scale). Confirms reading
   "current value" is inherently a *perturbing* read: you can't know a
   fader's position without moving it at least slightly first, there being
   no request/response query in this MCU implementation.
2. **Set to −12dB:** no dB-to-position curve exists in code, only three
   reference points in a docstring (`tools/mixer.py`: 0 = −∞dB, ~75 ≈ 0dB,
   100 = +12dB). Estimated `50.0` from a typical DAW fader-law rule of
   thumb. User read the actual display: **−11.7dB — 0.3dB off**, good
   enough. First real calibration data point for this curve, worth keeping:
   **level 50.0 ≈ −11.7dB**.
3. **Restore:** sent back the captured `84.33`. User confirmed it displays
   **+3.5dB**, consistent with the mouse position during the step-1 nudge
   (near the zero mark, not exactly on it) rather than some round number —
   makes sense given step 1 was a manual, imprecise nudge, not a return to
   a known value.

Whole cycle worked as asked, first time, live. No code changes from this
step — pure verification that §15's infrastructure does what it was built
for.

### 18. Found the actual protocol spec — confirms most of our implementation, catches two real bugs

The user found and shared the **Emagic Logic Control MIDI Implementation**
(User's Manual v2.0, Nov 2002, chapter 13, pp. 105–124) — Logic Control is
the same Mackie-licensed protocol family as MCU (SysEx header `F0 00 00 66
<model-id>`, manufacturer ID 00 00 66 = Mackie), so this is effectively the
authoritative spec for what we've been reverse-engineering/guessing all
session. Not reproduced verbatim here (copyrighted manual) — just the facts
extracted, same as every other external doc referenced this session.

**Confirmed correct, matches our implementation exactly:**
- Faders: pitch-bend (`Ei, ll, hh`) — matches, though the spec only requires
  10 of the 14 bits (positions 0–1023); we send full 14-bit precision, which
  doesn't hurt but is more than needed.
- Buttons/LEDs: Note On/Off (`90, ii, ss`, 7F=pressed/on, 00=released/off).
- REC/RDY (0x00–07), SOLO (0x08–0F), MUTE (0x10–17), SELECT (0x18–1F),
  Rewind/FF/Stop/Play/Record/Cycle, Bank navigation (0x2E–31) — every one of
  our existing note-number constants matches the spec table exactly.

**Two real bugs found by cross-referencing the ID table:**
- `_NOTE_SAVE` was `98` (0x62) — that ID is actually **Cursor Left** in the
  spec, not Save. Correct value: `0x50` (UTILITIES: SAVE).
- `_NOTE_UNDO` was `110` (0x6E) — that ID is actually **Fader Touch Ch. 7**,
  not Undo. Correct value: `0x51` (UTILITIES: UNDO).
- Fixed both in `midi_bridge.py`, updated the two affected tests
  (`test_save_sends_note_0x50`, `test_undo_sends_note_0x51`). Neither was
  ever verified live before — the mismatch went unnoticed because
  `transport_undo`/`transport_save` presumably just silently did nothing
  useful via MCU, or triggered the wrong button, and nobody had tested them
  specifically (Undo has separately been going through Ctrl+K/keyboard
  since §11, which is unaffected by this).
- `_NOTE_REDO` (`101`/0x65) also doesn't match anything sensible — 0x65 is
  **Scrub** in the spec, not Redo. Left unfixed: the reference spec has **no
  dedicated Redo button ID at all** in its table, so there's no known-correct
  value to put in its place. `transport_redo`'s MCU path is probably
  non-functional until this is investigated live against Studio Pro
  specifically (which could still deviate from the base spec).

**Other findings, not yet acted on:**
- **Metering is Channel Pressure (`D0, XX`), not CC** — channel (3 bits) +
  level 0–C=0–100%/E=set overload/F=clear overload (4 bits) packed into one
  byte. Also **not sent by default** — needs an explicit `Channel meter
  mode` SysEx (`<Hdr>, 20, ii, mm, F7`) sent first to enable it per channel.
  Direct, concrete input for the anti-clipping idea (§14) once that gets
  built — no more guessing needed for the message format itself, though
  Studio Pro's exact behavior still needs live verification.
- **LCD text (`<Hdr>, 12, oo, yy…, F7`) is SysEx** — this is how Studio Pro
  would push channel/track names to us, which could solve the "which
  channel is HELPERS" problem from §16 without asking the user for a
  channel number. But: python-rtmidi's `MidiIn` ignores SysEx by default
  (`ignore_types`), and `MidiBridge` never calls it to change that — so even
  if Studio Pro sends this, `_on_midi_in()` currently never sees it. Would
  need `self._in.ignore_types(sysex=False, ...)` plus a SysEx parser to
  actually use this.
- **V-Pot encoding is a relative delta** (`B0, 1i, XX` — direction bit +
  tick count, 0–63 ticks), not what `set_pan()`'s current CC-value formula
  looks like it's doing. Spotted as suspicious while cross-referencing but
  **not fully audited or fixed** — flagged for a dedicated look, not
  addressed this session.

Given tonight's machine instability (§17), none of the metering/LCD/V-Pot

  `C:\Users\adp\Documents\_MY_MUSIC_\FLSTUDIO\FL Studio\Settings\Hardware\
  MackieCU\device_MackieCU.py` (outside this repo, referenced not copied)

  **does** send the channel-meter-enable SysEx on every meter mode change,
  proving that message is legitimate spec-compliant behavior some hosts
  use — the earlier removal was reverted. This file also independently
  re-confirmed the meter byte format and the LCD text SysEx format
  (`F0 00 00 66 14 12 <offset> <text> F7`), a third independent source
  agreeing with the Nuendo capture and the Logic Control PDF.
- **The real crash cause, per the user's own hypothesis, was neither of the
  above**: our diagnostic scripts opened a connection, sent a handful of
  MCU messages, then just vanished — no handshake on connect, no cleanup on
  disconnect, unlike every real device/host. Studio Pro's MCU connection
  state was apparently left inconsistent by that. Added a
  `F0 00 00 66 14 1A 00 F7` "host connection query" on `open()` (what a
  real FaderPort sends on connect, per the Nuendo capture) and a cleanup
  burst on `close()` (disable all channel meters + blank both LCD lines,
  mirroring FL Studio's `OnDeInit`). This alone introduced a **new**, real
  bug — the cleanup burst's self-echoed SysEx (loopMIDI echoes our own
  sends back to us) raced `close_port()` on Windows and deadlocked the
  process indefinitely, even with `cancel_callback()` called first. Fixed
  with a 100ms drain delay before closing. Verified 3/3 clean exits, then
  live: **FSP played a full song with metering live-verified across all 8
  channels for 15s, then the connect/disconnect cycle completed cleanly —
  user confirmed FSP was "dokonale stabilní" (perfectly stable)
  afterward.** This appears to have been the actual root cause of the
  instability that plagued the earlier parts of the day (and the dB
  calibration session before that) — not any specific SysEx message, just
  the missing handshake/cleanup around the connection lifecycle.
- **LCD text channel-name reading**, the last big item: implemented SysEx
  parsing (`_handle_lcd_text`), unit-tested against real captured bytes,
  but the first live test came back wrong — `select_channel(0)` (channel 0
  = "PERCS" per the user) returned `{0: '<C>', 7: 'Simple'}`, neither of
  which is a channel name. Root-caused via raw traffic logging: Studio
  Pro's LCD display semantics are **display-mode-dependent** —
  `select_channel()` puts it into "Pan Focus Mode" with a "Simple" panner
  type, where the *label* row's last slot (7) holds the *selected*
  channel's name (not slot 0, and not literally "channel 7"), the *value*
  row's first slot (0) holds that channel's pan reading, and slot 0 of the
  *label* row holds a static "Pan L/R" title unrelated to any channel —
  this static title is exactly what broke the first detection attempt
  (`label_populated == [7]` was actually `[0, 7]`). Fixed by keying off
  slot 7 alone. Live-verified **8/8 channels correct** against a
  user-supplied ground-truth mapping (Studio Pro's own 7-character
  abbreviation of longer names, e.g. "Kick _01" → "Kick_01", "Ambient
  Snare_01" → "AmbntSn" — dropping vowels/spaces to fit).
