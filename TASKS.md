Jednotkově otestováno (`TestChannelMetering`, 193/193 testů zelených). **Živý test (`diag_meter.py` ve scratchpad, throwaway):** povoleno metering na kanálu 0, 20s poslechu — nepřišla žádná `D0` zpráva, jen self-echo vlastního SysEx z loopMIDI. Nejasné proč: (a) hrálo vůbec něco na kanálu 0 během testu?, (b) SysEx model ID `0x14` (Mackie Control Universal) možná není to, co Studio Pro pro tuhle konkrétní zprávu očekává — spec je pro Logic Control hardware (`0x10`), ne obecné MCU; nemáme potvrzeno, který Studio Pro skutečně vyžaduje, (c) FSP spadlo hned po testu (podobná nestabilita jako u dB kalibrace) — nejisté, jestli test proběhl čistě předtím, nebo jestli nestabilita ovlivnila výsledek. Žádný z těchto bodů zatím vyloučen. **Podezření (2026-08-08, nepotvrzeno):** tohle byl vůbec první SysEx, který náš kód kdy živě poslal do FSP — všechny dosavadní testy (play/stop, fadery, SAVE/UNDO/REDO) používaly jen Note On/Off a Pitch Bend, běžné/dobře otestované MCU zprávy. `enable_channel_meter()` posílá neověřený formát (model ID `0x14` je odhad — spec je doslova pro Logic Control hardware `0x10`, ne potvrzeno že Studio Pro na `0x14`/command `0x20` reaguje stejně). Možné, že FSP nemá SysEx parsing robustní a neplatná/neočekávaná SysEx zpráva ho fakticky shodila. Netestováno dost na jistotu — koreluje časově, nic víc. Až se bude pokračovat: než znovu zkoušet metering naživo, zvážit opatrnější přístup (např. nejdřív ověřit, že FSP vůbec nějakou SysEx zprávu z nás přežije, třeba kratší/neškodnější, a mít čerstvě restartovaný stroj). Nepřičítat automaticky kódu bez dalších důkazů, ale brát vážně jako hlavní podezřelý.

- [x] **Opravit `set_pan()` V-Pot relative CC encoding (skutečný bug, 2026-08-08).** Audit odhalil, že záporný pan (doleva) se kódoval **obráceně**: stará formule `64 + (64 + pan)` dávala menší tick count pro *větší* výchylku doleva a naopak (např. pan=-1 → tick 63, pan=-64 → tick 0).
